## 已证实的代码问题

- HeadphoneMotion.start() 在设备暂不可用、OS 仍认为 active 时返回。AppModel.activate() 又在 loop 已存在时直接返回，缺少稍后就绪/中断后重试。现有循环读状态却不能恢复采集。
- MotionProbe.referenceChanged 是显示参考的锁存状态，成功样本也不恢复 look。它和 TrackingController 的运动校准不同，不能据此把 53.6Hz 源回调描述成没有数据。
- 后台主动执行 app_background 全会话关闭；activate 没有原相机恢复路径，用户必须重新开始搜索/配对。
- CalibrationSheet 以带毫秒数的完整错误文字作 ForEach 身份，313ms→386ms 会改变 SwiftUI 身份；并且校准中用 ProgressView 替换原按钮，状态区高度变化会挤动操作区域。
- 录像请求已有4秒退出机制，并非无期限 pending。真正回报超过2秒时 actualRecording 为 nil，会禁用入口；原适配器没有状态订阅恢复和清楚的当前阻塞说明。跟随校准本来不应是录像前提，仍保持独立。

## 本轮修改

1. activate 总是先核对采集与相机恢复，再决定是否创建唯一控制循环。采集恢复复用现有循环，每次前台周期最多3次实际启动，活动但无新样本的服务有独立恢复等待；设备未就绪/权限拒绝不循环启动。200ms 安全停止条件未变。
2. 新鲜真实头部输入到达后，可重建显示观察零点；不会改 TrackingController 校准、自动开始或吞掉参考跳变。当前采集、等待样本、服务未启动和跟随校准分别显示与记录。
3. 短暂 inactive 只停运动，保留仍有效的会话/校准；background 停运动和采集、使原校准失效，关闭传输并仅在内存保留原设备/SSID。返回前台单次有限恢复，先检查网段、identity-only 打开和真实 GetSSID 回报，匹配原设备后才注册与启动预览。无网段、身份不符或20秒未完成均停止并给出具体提示；原设备重试不经过搜索。进程被杀后不伪装拥有旧会话，正常选择设备连接。
4. 显式系统设置 Wi-Fi 交接保留既有等待流程。恢复通信和预览不等于恢复跟随，仍需校准与明确开始。未添加后台权限/持续后台运行。
5. 相机姿态继续沿 build18 UDP最新槽与真实入口时间，不扩大200/300ms、0.7秒/15样本/12秒要求。姿态或录像回报确实过期时，最多3次按原协议、原键和ID恢复只读状态订阅，不初始化云台、不伪造回报。需要时用户可明确“重新获取相机状态”。这不是已证明所有镜头源间隔会缩短的承诺。
6. 校准错误使用稳定原因ID；操作区始终存在，锚定底部，进度占固定空间；取消状态变化的非必要动画。预览渲染器、视频视图实例入口和玻璃样式保持原样。真实失效立即停止并禁用危险操作，不做可用性防抖或假可用。
7. 录像当前阻塞单独显示，超时记录精确事件；只有相机新鲜状态回报才恢复操作，不以目标/请求代替实际状态。
8. schema7 向后保留 schema6 的姿态阶段时间、源间隔和 Main 交付延迟，并加前后台状态、采集服务/恢复次数、网络证据、录像时效和拒绝原因；不含密码。源物理采样时刻、内核包到达时间仍未知。

## PR #1 的逐项取舍

仍为独立 OPEN 分支，未整包合并。仅采用已检查的相关改动：

- CameraHealth 的独立控制/视频接收证据：入站仍活跃时，单一 writeHealthy 标志不能触发整机误断；真实全传输失败仍按原1秒判断。
- NWPath/相机网段观察和真实 heartbeat 视频/重建上下文，避免空上下文和永久 holdsMonitor。
- VideoRecoveryPolicy 在控制回报新鲜时不升级成共享 UDP 重建；保留有界视频修复、明确暂停与手动重试。控制随后确实失效时才允许最后一次共享修复。

没有合入机身/镜头四元数研究、移动事件记录页、安装方式或挂脖控制。1∶1 数学、倍率、协议编码、范围和已保存参数不改。

## 最短真机验收与尚缺证据

1. 原 Sideloadly 账户覆盖，不卸载。更多→关于 HeadLink，核对1.2.4、构建号与提交。
2. AirPods保持系统连接，先仅连接相机并预览。切到其它App再返回：检查运动采集自动恢复、原相机通信及新帧恢复，跟随始终停止；无相机网段按提示在系统设置加入原Wi-Fi，再点“恢复原相机通信与预览”。不要先搜索/重复配对。打开控制中心等短暂失活另测一次；后台恢复与短暂失活不是同一校准规则。
3. 固定机身打开校准面板，输入暂时失效再恢复时检查按钮位置和当前原因；稳定后完成校准→明确开始→左右/上下→保持/回基准→暂停。打开关闭普通设置不能重建会话；打开校准入口本来就明确暂停，采样中拖走面板仍取消该次校准。
4. 跟随未校准时单独开始/停止录像，核对相机实际响应；再在跟随运行时分别操作，至少连续运行5分钟。

仍需一次真实运行诊断来定位303/386ms的来源。现有 build18/schema6 的“更多→本地诊断→生成脱敏诊断文件→分享JSON”已经能提供版本/提交、lastValidIngressAt/lastValidGap、lastParsedAt、lastDeliveredIngressAt/lastDeliveryLag、loopGap、headSensorTime与源回调统计；本轮schema7还加入恢复和网络/录像状态。异常发生后立刻导出即可，无需重新口述视频现象。若lastValidGap越界但解析和Main延迟低，只能确认App入口观测到遥测稀疏，不能区分无线/相机内部/OS投递；那一步可能还需要相机端日志或网络抓包，届时只补相应证据，不改阈值掩盖。
